# Физический уровень и аппаратные режимы

Имитационная модель сохраняется без подмены её результатов аппаратными измерениями. Дополнительно реализованы физический программный I/Q-стенд, профиль **двух PlutoSDR** и отдельный профиль **платы LX2160A**.

## Что работает и что требует плат

| Часть | Реализовано | Как проверено |
|---|---|---|
| Физические биты, CRC-16, свёрточный код, puncturing, CC/IR | Python | Известные CRC-векторы, битовые тесты, полный I/Q round-trip |
| Преамбула, BPSK, CFO/фазовая синхронизация, LLR, Витерби | Python | Разрезанные буферы, фазовый/частотный сдвиг, шум |
| DATA/ACK/NACK с защищённым заголовком | Python | Физический I/Q обмен в обоих направлениях |
| Два Pluto, RX/TX через pyadi-iio/libiio | Реальный адаптер | Интерфейс и отсутствие автоматического fallback; RF на платах не проверен |
| Агент LX2160A | Linux-сервис, Python/aarch64 | Локальные API, аутентификация, контракт данных; на LX2160A не развёрнут |
| RF/DMA платы | Хостовая сторона UDP/IQ-контракта | Фрагментация, CRC, перестановка фрагментов, дубликаты |
| HARQ-таймер в FPGA | Синтезируемый эталонный SystemVerilog | Icarus Verilog: ACK, устаревший tag, timeout, backpressure |
| FPGA modem, AXI/DMA, bitstream конкретной платы | Не реализованы | Нужны модель платы, FPGA, RF-модуль и HDL-проект |

Работа драйвера без аппаратной проверки не означает готовый сертифицированный радиомодем. В GUI это явно отмечено; отсутствующее устройство вызывает ошибку, а не переход в имитацию.

## 1. Физический стенд без оборудования

```sh
uv run harq-lab hardware configs/hardware_iq.json --output results/hardware-iq.json
```

Здесь **не используется BLER-кривая** сетевого симулятора. Передаются реальные кодированные биты и комплексные отсчёты. AWGN добавляется к I/Q, затем выполняются обнаружение преамбулы, восстановление несущей, получение LLR и soft Viterbi. Обратный ACK/NACK также проходит через BPSK/IQ и синхронизатор.

Поле `snr_db` — Es/N0 при символьной скорости; дисперсия шума на отсчёт учитывает `samples_per_symbol`. Фазовый сдвиг и небольшое смещение частоты в программном канале нужны для проверки синхронизации. При низком SNR заголовок может не обнаружиться; тогда отправитель видит timeout. Это не подменяется NACK из вероятностной модели.

Алгоритмы: один процесс Type-I, Parallel Type-I, CC, IR. Адаптивная эвристика сетевой модели в аппаратном режиме недоступна: её прогнозы сначала нужно откалибровать по измеренной BLER и задержкам.

## 2. Стенд из двух PlutoSDR

Роли:

```text
HARQ TX → Pluto №1 TX ── RF данные ──→ Pluto №2 RX → CRC/FEC
HARQ TX ← Pluto №1 RX ←─ RF ACK/NACK ─ Pluto №2 TX ← приёмник HARQ
```

Оба устройства управляются одним процессом на хосте. На каждый Pluto используются отдельные IIO-контексты RX и TX. Начальные URI в конфигурации — примеры, их нужно заменить на адреса реально подключённых устройств. Адреса должны различаться.

Установите системную libiio по инструкции Analog Devices, затем Python-зависимости:

```sh
uv sync --python 3.12 --extra hardware --extra dev
```

В GUI: «Аппаратный стенд» → «Два PlutoSDR». Кнопка чтения IIO-контекста не создаёт TX-буфер. Для полноценного HARQ нужно разрешить передачу: приёмник тоже передаёт ACK/NACK.

```sh
uv run --extra hardware harq-lab hardware configs/pluto_pair.json --output results/pluto-pair.json
```

Команда действительно включает TX. Сначала подготовьте согласованное соединение/ослабление и подходящий диапазон. Начальное ослабление TX — −50 dB. В данном адаптере циклическая передача выключена: каждый кадр отправляется конечным буфером.

Частота дискретизации, LO и RF-полоса должны совпадать на обоих устройствах. Пакетный обмен реализован на хосте; штатная прошивка Pluto не заменяется. Не моделируются калиброванные дальность и задержка распространения. `feedback_delay_ms` — дополнительное ожидание у приёмника, оно не называется физической дальностью.

Ограничения эталонного модема: прямоугольные импульсы BPSK, простая символьная синхронизация без полноценного timing recovery, ограниченный поиск CFO, нет эквалайзера многолучевого канала и адаптации частоты дискретизации. Для первых проверок нужен короткий стабильный стендовый канал. RF-фильтры, независимые генераторы и USB/DMA могут потребовать доработки синхронизации на реальном стенде.

## 3. Отдельный режим платы LX2160A

LX2160A — сетевой ARM-процессор. Он не заменяет RF-трансивер или FPGA. Для второго режима на плате работает отдельный агент. Интерфейс Electron остаётся на компьютере.

На Linux/aarch64 скопируйте проект в `/opt/harq-lab`, создайте окружение и задайте токен:

```sh
uv sync --python 3.12
export HARQ_AGENT_TOKEN="replace-with-a-random-secret-at-least-24-characters"
uv run harq-lab device-agent --port 8766
```

Агент слушает только loopback. На компьютере откройте SSH-туннель:

```sh
ssh -N -L 8766:127.0.0.1:8766 user@BOARD_ADDRESS
```

В GUI выберите «Плата LX2160A», адрес `http://127.0.0.1:8766` и токен. Токен не сохраняется в истории, конфигурации или экспортируемых результатах.

Доступные режимы платы:

- Программная проверка физического тракта на CPU платы — не требует RF и не выдаётся за измерение радио.
- Передатчик HARQ через RF/DMA UDP/IQ.
- Приёмник HARQ с формированием ACK/NACK через тот же интерфейс.
- RX-only захват I/Q.

Для двух последних направлений требуется внешний радиотракт. Реализация зависит от модели платы, RF-модуля, драйвера DMA/PCIe/Ethernet и FPGA. Проект предоставляет проверяемый контракт, но не выдумывает неизвестный vendor driver.

Шаблон systemd: `deploy/lx2160/harq-agent.service`. Создайте пользователя `harq`, разместите токен в `/etc/harq-agent.env` с ограниченными правами и проверьте пути перед включением сервиса. DPAA2, NEON-оптимизация и real-time Linux не предполагаются автоматически.

## RF-кадр HQR1

Преамбула: фиксированная PN-последовательность длиной 32 BPSK-символа, повторённая дважды. По ней оцениваются начало кадра, грубое/остаточное смещение частоты и фаза. После преамбулы работает training-aided/decision-directed Costas loop.

Заголовок — big-endian `!4sBBBBIIHHI`, затем CRC32 заголовка. Биты заголовка повторяются по три раза и складываются мягко:

| Поле | Размер | Значение |
|---|---:|---|
| magic | 4 | ASCII HQR1 |
| version | 1 | 1 |
| kind | 1 | 0 DATA, 1 ACK, 2 NACK |
| mode | 1 | 0 Type-I, 1 CC, 2 IR |
| attempt | 1 | 1…8 |
| packet | 4 | Идентификатор пакета |
| process | 4 | HARQ-процесс, 0…31 |
| payload_bytes | 2 | Длина полезных данных |
| coded_symbols | 2 | Число передаваемых символов после puncturing |
| session | 4 | Случайный идентификатор сеанса |
| header CRC32 | 4 | CRC32 предыдущих полей |

Полезная нагрузка DATA: CRC-16/CCITT-FALSE, свёрточный mother-code K=3, полиномы (7,5), два хвостовых нуля. Первая передача использует паттерн [1,1,1,0]. CC повторяет этот паттерн. IR во второй попытке передаёт пропущенные позиции, затем mother-code целиком. LLR раскладываются по одним и тем же позициям mother-code и складываются. Type-I сбрасывает наблюдения предыдущей попытки.

ACK/NACK — защищённый заголовок без тела. Если заголовок DATA повреждён, приёмник не знает надёжно идентификатор пакета и не отправляет NACK: передатчик использует timeout. Обратная связь принимается только при совпадении session, process, packet, attempt и mode. Уже доставленные данные повторно не учитываются; потерянный ACK может вызвать повторную передачу доставленного пакета.

## Контракт RF/DMA платы: HIQ1

`harq_lab/hardware/board.py` реализует UDP-фрагментацию I/Q. Это **контракт проекта**, не существующий стандарт NXP.

Каждая датаграмма: заголовок `!4sBBHIIHHI`, затем полезная нагрузка, затем big-endian CRC32 заголовка+нагрузки.

| Поле | Размер | Назначение |
|---|---:|---|
| magic | 4 | HIQ1 |
| version / kind | 1 + 1 | 1; kind=1 TX IQ, kind=2 RX IQ |
| bytes | 2 | Длина payload этой датаграммы |
| session / sequence | 4 + 4 | Сеанс и номер I/Q-буфера |
| fragment / total | 2 + 2 | Индекс фрагмента с нуля и число фрагментов |
| sample_rate | 4 | Частота дискретизации |

Payload: little-endian `complex64` (float32 I, float32 Q), нормализованные отсчёты. Один фрагмент — до 128 комплексных отсчётов, 1024 байт. Получатель восстанавливает буфер с проверкой CRC, размера, числа фрагментов, частоты, перестановок и дубликатов. Незавершённая сборка устаревает через 2 с. UDP-источник фильтруется по заданной паре IP/port. CRC не является аутентификацией: этот канал предназначен для изолированной сети стенда/локального RF-сервиса.

RF/DMA-сервис должен принять TX IQ из этого контракта и доставить их на DAC, а RX IQ с ADC отправить на указанный локальный порт агента. Он должен управлять LO, усилением и полосой своего реального радиотракта. Текущий UDP-пакет не передаёт эти настройки: они конфигурируются в самом RF/DMA-сервисе. Без этого сервиса реальный обмен на LX2160A не начнётся, а будут наблюдаться таймауты.

## FPGA

`fpga/harq_timer.sv` — модуль управления таймерами процессов с поколениями/tag. Он выдаёт ACK, NACK или TIMEOUT и сохраняет событие при backpressure. Это не весь PHY и не готовая прошивка Pluto.

```sh
iverilog -g2012 -o /tmp/harq-timer.vvp fpga/harq_timer.sv fpga/tb_harq_timer.sv
vvp /tmp/harq-timer.vvp
```

Для реального переноса в PL нужны модем, синхронизация, CRC/FEC, память мягких решений, DMA/AXI-интерфейс, clock/reset, разводка и constraints выбранной платы. Таймер ожидает сигналы valid/ready и корректно сформированный tag от такого контроллера. Текущее ядро не подключается к IIO автоматически.

## Метрики и часы

В аппаратном режиме время берётся из monotonic clock хоста. Оно включает Python, синхронизацию, декодирование, очереди, IIO/UDP и обратный путь. Метрика `ack_p95_host_ms` — время от начала обработки пакета до ACK на хосте, не one-way latency радиоканала. `acked_goodput_kbps` — скорость подтверждённых полезных бит. Пакет без ACK после лимита отмечается `unacknowledged`: это не доказывает потерю на приёмнике.

Результат содержит `source`, исходную конфигурацию и отдельные счётчики TX/RX. Поля `hardware_verified_by_developer=false` и данные capabilities не меняются на true после программного теста. Для экспериментов с точным RTT нужны аппаратные временные метки и согласованный способ синхронизации часов, которых пока нет в этом адаптере.
